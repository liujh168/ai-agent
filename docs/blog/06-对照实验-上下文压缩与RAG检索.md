## 一、实验设计：两组对照，各自回答一个问题

| 实验 | 对照组 | 回答的问题 | 依赖 |
|------|--------|-----------|------|
| 实验 1：上下文压缩 | A 不压缩 / B LLM 摘要 / C 硬截断回退 | 压缩到底省多少字符（≈token）？ | 字符数对比无需 API；真实摘要质量需 LM Studio |
| 实验 2：RAG 检索 | 纯 Python 余弦 vs FAISS IndexFlatIP | FAISS 快多少？结果一致吗？ | 完全本地，用确定性假 embedding |

实验 2 有一个重要前提要说清楚：本项目 RAG 的两条检索路径**语义一致**——都是余弦相似度 top-k（`rag.py:168-176` 里只是 `if self._faiss_index is not None` 分流）。所以这组实验的价值是**耗时对比 + 一致性验证**，不是"检索质量对比"。项目也没有实现混合检索（向量 + 关键词），本文不会假装它有。

## 二、实验 1：上下文压缩效果对比

### 2.1 被测对象

`ai_agent/client.py:240-295` 的 `summarize_messages()`：history 总字符超过 `history_max_chars`（`config.py:79`，默认 5000）时，保留最近 4 条完整消息，较早历史交给 LLM 做 200~300 字摘要；摘要调用失败则回退为硬截断（丢弃旧历史，插入 `【历史已截断】` 占位）。

### 2.2 方法

`experiments/compression_benchmark.py` 构造一段**确定的合成对话**（40 轮关于本项目实现细节的问答，81 条消息），然后跑三个对照组：

- **A. 不压缩**：原始历史原样计算字符数
- **B. LLM 摘要压缩**：真实调用 `summarize_messages()`。脚本自动检测 LM Studio：服务可用就走真实摘要；不可用则用一条 250 字符的确定性文本模拟摘要输出——**字符数对比依然真实**（因为摘要的目标长度就是 prompt 里写死的 200~300 字），只是摘要质量无从谈起
- **C. 硬截断回退**：让 `client.chat` 抛异常，走真实的失败回退代码路径（`client.py:282-293`），这条路径完全不需要 API

### 2.3 结果

以下是在本机（无 LM Studio，模拟摘要模式）真实运行的输出：

```
========================================================
  实验设置：合成对话 40 轮（81 条消息，6384 字符）
========================================================

========================================================
  结果汇总（字符数 = sum(len(m.content))，中文 1 字符 ≈ 1~2 token）
========================================================
  方案                                    消息数      字符数     相对原始
  --------------------------------------------------------------
  A. 不压缩（原始历史）                           81     6384   100.0%
  B. LLM 摘要压缩（模拟 250 字符摘要）                6      593     9.3%
  C. 硬截断回退（摘要失败时）                         6      376     5.9%
```

真实 LLM 摘要对比（表格模板，请用 `--llm` 模式运行后自行填写，本文不编造数据）：

| 方案 | 消息数 | 字符数 | 相对原始 |
|------|-------:|-------:|---------:|
| A. 不压缩 | 81 | 6384 | 100.0% |
| B. LLM 摘要压缩（真实） | _待填_ | _待填_ | _待填_ |
| C. 硬截断回退 | 6 | 376 | 5.9% |

运行 `python experiments/compression_benchmark.py --llm`（需 LM Studio 加载聊天模型）即可获得真实摘要对比，脚本还会打印摘要全文供人工检查质量。

### 2.4 结论

1. **压缩的字符收益是数量级的**：6384 → 593 字符（9.3%），约省下 91% 的上下文。按"1 中文字 ≈ 1~2 token"粗略换算，一次压缩把 ~6k~13k token 的历史压到 ~600~1200 token。对话越长，收益越大——因为成本是固定的（4 条最近消息 + 一条 300 字摘要），被压掉的旧历史是线性增长的。
2. **硬截断比摘要再省一点（5.9% vs 9.3%），但代价是信息全丢**。B 组保留了"关键事实、决定、待续事项"（摘要 prompt 里明确要求保留时间、数字、名字），C 组只剩一句"较早的 76 条消息被丢弃"。**省下的 3.4 个百分点买的是"完全失忆"**——这就是为什么回退路径只该是兜底，不该是常态。
3. 压缩不是免费的：B 组要多付一次 LLM 调用（max_tokens=512）。这是一笔"用一次摘要调用的 token，换后续每轮对话的输入 token"的买卖，长会话下稳赚。

## 三、实验 2：RAG 检索方式对比（numpy vs FAISS）

### 3.1 被测对象

`ai_agent/rag.py`：

- numpy 路径：`search_detailed()` 里纯 Python 逐向量算余弦（`rag.py:170-176`），O(N) 全扫描
- FAISS 路径：`_build_faiss_index()`（`rag.py:186-200`）在 chunk 数 > `faiss_threshold`（默认 2000）时构建 `IndexFlatIP` 索引，检索走 `rag.py:202-217`

### 3.2 方法

`experiments/rag_benchmark.py` 用**确定性假 embedding**（文本 md5 作随机种子，384 维高斯向量）生成 N 个 chunk——同一文本永远得到同一向量，完全不需要 embedding 服务。通过设置 `faiss_threshold=10**9` / `0` 强制走 numpy / FAISS 路径，各跑 50 次 top-5 查询计时，并逐查询比对两条路径返回的 `chunk_index` 列表。

### 3.3 结果

以下为真实运行输出（Windows，Python 3.12，faiss-cpu 1.15.1，numpy 2.2.6）：

```
========================================================
  实验组：N = 500 个 chunk（向量维度 384，查询 50 次）
========================================================
  numpy 路径（纯 Python 余弦全扫描）: 总耗时   0.74s，平均    14.9 ms/查询
  FAISS 路径（IndexFlatIP）:           总耗时   0.01s，平均     0.1 ms/查询
  加速比: 119.7x
  结果一致性: top-5 完全一致的查询 50/50，平均重叠 5.00/5

========================================================
  实验组：N = 5000 个 chunk（向量维度 384，查询 50 次）
========================================================
  numpy 路径（纯 Python 余弦全扫描）: 总耗时   7.50s，平均   150.0 ms/查询
  FAISS 路径（IndexFlatIP）:           总耗时   0.01s，平均     0.3 ms/查询
  加速比: 591.6x
  结果一致性: top-5 完全一致的查询 50/50，平均重叠 5.00/5
```

| chunk 数 | numpy 平均耗时 | FAISS 平均耗时 | 加速比 | top-5 一致率 |
|---------:|---------------:|---------------:|-------:|:------------:|
| 500 | 14.9 ms | 0.1 ms | 120x | 50/50 完全一致 |
| 5000 | 150.0 ms | 0.3 ms | 592x | 50/50 完全一致 |

（耗时是相对的——不同机器绝对值会不同，但"numpy 路径随 N 线性增长、FAISS 基本持平"这个趋势是结构性的。）

### 3.4 结论

1. **numpy 路径耗时与 N 严格线性**：500 → 5000（×10），14.9 → 150.0 ms（×10）。这就是 O(N) 全扫描的样子。N=5000 时单次查询 150ms，已经能在交互里感觉到卡顿——而 RAG 检索发生在 Agent 的工具循环中间，后面还排着 LLM 调用。
2. **FAISS 几乎不随 N 增长**：0.1 → 0.3 ms。加速比从 120x 涨到 592x——**chunk 越多，FAISS 越值**。
3. **两条路径结果完全一致**：50/50 查询 top-5 完全相同。这验证了 FAISS 路径的语义等价性（float32 舍入差没有影响排序），`faiss_threshold` 切换是安全的。
4. 回头看 `faiss_threshold=2000` 这个默认值：N=500 时 numpy 也只要 15ms，完全够用；N 到几千以后 numpy 才开始拖后腿。阈值留在 2000 是合理的——**小库不付 FAISS 的依赖和构建成本，大库自动升级**。现在这条决策有数据了。

## 四、如何复现

```bash
# 实验 2：RAG 检索对比（纯本地，无需任何服务）
.venv/Scripts/python experiments/rag_benchmark.py
# 自定义档位：
.venv/Scripts/python experiments/rag_benchmark.py --sizes 1000 10000 --queries 50

# 实验 1：上下文压缩对比
# 字符数对比（无需 API，模拟摘要 + 真实硬截断路径）：
.venv/Scripts/python experiments/compression_benchmark.py
# 真实 LLM 摘要对比（需 LM Studio 运行并加载聊天模型）：
.venv/Scripts/python experiments/compression_benchmark.py --llm

# faiss 未安装时：
pip install -e .[faiss]
```

两个脚本都不写任何文件、不碰 `.env`、不消耗 API 额度（`--llm` 模式除外，它只对本地 LM Studio 发请求）。

## 一、架构模式与代码组织

### A1 · 单一真相源（Single Source of Truth）

- **源代码位置**：`ai_agent/app_core.py`
- **决策内容**：`app_core.py` 集中定义 `SYSTEM_PROMPT`、`TOOL_SCHEMAS`、`build_tool_map()`、`build_tool_executor()`、`filter_tool_schemas()`，CLI（`main.py`）与 Web UI（`web_ui.py`）均从此处引用。
- **关键代码片段**：

```python
# app_core.py L97-L400 — TOOL_SCHEMAS 列表是 Function Calling 的"真相源"
TOOL_SCHEMAS = [
    {"type": "function", "function": {
        "name": "get_weather",
        "description": "查询指定城市的天气",
        "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]},
    }},
    # ... 共 21 个 schema，CLI 和 Web UI 都只引用这一份
]

# 自动计数，banner / README / Web 标题都引用它
TOOL_COUNT = len(TOOL_SCHEMAS)  # L405
```

- **设计意图**：历史上 CLI 和 Web UI 各自维护一份 system prompt 与工具列表，随项目演进逐渐漂移——例如 prompt 漏写 `plan_task` / `extract_structured` 路由指令导致评测必失败、Web 端工具数量文案三处打架（18 / 20 / 实际 21）。抽出统一模块后彻底消除重复实现漂移问题。
- **权衡分析**：
  - ✅ 好处：零漂移风险，新增工具只需改一处，文案自动同步
  - ❌ 代价：`app_core.py` 变成"上帝模块"，文件较大（约 650 行）
  - 对比方案：按功能拆成多个模块（如 `prompts.py` / `schemas.py` / `factory.py`），但 CLI 和 Web UI 仍然要跨模块 import，实际分散认知负担
- **影响范围**：`main.py`、`web_ui.py`、`eval.py` 均通过 `from ai_agent.app_core import ...` 引用；README banner、启动日志、Web 页面标题均依赖 `TOOL_COUNT`
- **演进方向**：当工具数量超过 50 时，可考虑按 domain 拆分 `schemas/` 子目录，每个 domain 一个模块，`app_core.py` 只做聚合导出

### A2 · 工厂函数模式构建 Tool Map

- **源代码位置**：`ai_agent/app_core.py` → `build_tool_map()` (L444-L580)、`build_tool_executor()` (L583-L606)、`filter_tool_schemas()` (L609-L625)
- **决策内容**：三个工厂函数统一完成工具注册、执行器装配、schema 过滤三件套。`build_tool_map()` 接受 `client`、`get_rag`、`get_history` / `set_history`、`mcp_manager` 等依赖参数，闭包方式绑定到工具实现上。
- **关键代码片段**：

```python
# app_core.py L468-L479 — 纯函数 vs 闭包的装配差异
def workspace_file_read(path: str, max_chars: int = 3000) -> str:
    return file_read(path, max_chars=max_chars, workspace_root=workspace_root)
workspace_file_read.__name__ = "file_read"   # 保留 Function Calling 的工具名
workspace_file_read.__doc__ = file_read.__doc__
tool_map["file_read"] = workspace_file_read

# app_core.py L493-L498 — 需要 client 的闭包工具
def demo_stream_chat(topic: str) -> str:
    lines = []
    for token in client.chat_stream([{"role": "user", "content": topic}]):
        lines.append(token)
    return "已在上方以流式方式直接展示完整输出。" if lines else "（无流式输出）"
tool_map["demo_stream_chat"] = demo_stream_chat
```

- **设计意图**：把"纯函数工具"和"需要 client 的闭包工具"统一到一个入口装配，CLI/Web UI 通过参数注入各自的访问器，避免两份 tool_map 维护。
- **权衡分析**：
  - ✅ 好处：依赖注入清晰，`workspace_root` / `client` / `rag` 都由调用方决定
  - ❌ 代价：闭包工具调试时看不到 `__closure__`，需要额外 `.__globals__` 查看
  - 对比方案：把所有工具做成类实例方法，依赖在 `__init__` 注入——但 Function Calling 只接受 `{name: callable}`，类实例方法仍然需要再包装一层
- **影响范围**：CLI、Web UI、评测、AgentRuntime 都通过工厂获取 tool_map；`summarize_history` 是否注册取决于是否传入了 `get_history` / `set_history`
- **演进方向**：引入显式的 `ToolDescriptor` 类（包含 name / schema / callable / dependencies），替代当前"纯 dict + 闭包"的隐式结构

### A3 · 轻量 dataclass + 类型标注代替完整框架

- **源代码位置**：`config.py` → `Config`、`persistence.py` → `Session`、`tooling.py` → `ToolPolicy` / `ToolExecution`、`events.py` → `AgentEvent`、`skill.py` → `SkillDef`、`eval.py` → `EvalCase` / `EvalResult`
- **决策内容**：所有数据结构均用 `@dataclass(frozen=True)` + `typing.Literal` 类型别名声明，不引入 Pydantic 等重依赖。
- **关键代码片段**：

```python
# tooling.py L10-L18 — Literal + frozen dataclass 的组合
RiskKind = Literal["read", "write", "execute", "mcp"]

@dataclass(frozen=True)
class ToolPolicy:
    allow_write: bool = True
    allow_execute: bool = False
    allow_mcp: bool = True
    confirm_write: bool = False
    confirm_execute: bool = True
    confirm_mcp: bool = True
    mcp_allowlist: frozenset[str] | None = None
```

- **设计意图**：保持项目依赖精简（仅 openai / requests / gradio / pypdf / pillow 等必要包），frozen 保证不可变性，避免运行时被误修改。
- **权衡分析**：
  - ✅ 好处：零额外依赖、实例不可变可安全传递、IDE 类型提示友好
  - ❌ 代价：frozen dataclass 没有 Pydantic 的自动类型转换/校验；`frozenset[str]` 构造时要手动 `frozenset(iterable) or None`
  - 对比方案：用 Pydantic v2——获得 `model_validator` / `computed_field` 等功能，但安装体积增加，且 Pydantic v1/v2 差异大
- **影响范围**：全项目所有数据结构——Config / Session / AgentEvent / ToolPolicy / ToolExecution / SkillDef / EvalCase / EvalResult / RetrievedChunk / MCPTool / MCPError 全部采用此模式
- **演进方向**：若未来需要复杂字段校验（如 `Config.base_url` 必须是合法 URL），可在 dataclass 上添加 `__post_init__` 手动校验，无需引入 Pydantic

### A4 · 模块级纯工具 + 闭包工具分离

- **源代码位置**：`ai_agent/tools/__init__.py`、`ai_agent/tools/demo.py` / `fs.py` / `search.py` / `sql.py` / `system.py`；`ai_agent/app_core.py` → `build_tool_map()` 内闭包
- **决策内容**：无状态的纯函数工具放在 `tools/*.py` 子模块；需要访问 client / rag / history 的能力作为闭包在 `build_tool_map()` 内部定义。
- **关键代码片段**：

```python
# tools/__init__.py L15-L19 — 统一 re-export，外部通过 from ai_agent.tools import xxx 引用
from .demo import calculator, get_weather
from .fs import file_read, file_write
from .search import web_search
from .sql import sql_query
from .system import human_confirm, run_code, run_terminal

# app_core.py L572-L573 — summarize_history 的条件注册
if get_history is not None:
    tool_map["summarize_history"] = make_summarize_history(client, get_history, set_history)
```

- **设计意图**：纯工具可独立测试、可被多入口复用；闭包工具绑定了 client 依赖，随 tool_map 一起装配。
- **权衡分析**：
  - ✅ 好处：`calculator()` 可以直接 `pytest tools/test_demo.py` 独立测试；闭包工具的依赖由调用方决定（CLI 用文件 history，Web UI 用 thread-local history）
  - ❌ 代价：同一个工具名在不同入口下行为可能不同（如 `summarize_history` 在评测环境不存在）
  - 对比方案：把所有工具统一做成类实例方法——但会导致 client / rag 等依赖传递链变长
- **影响范围**：tools/ 子目录全部文件；app_core.build_tool_map()；EvalCase 的 expected_tool 判定需要考虑"工具是否在此入口被注册"
- **演进方向**：在 tool_map 构建后增加一个 `validate_tool_schemas(map, schemas)` 检查，确保 LLM 会看到的 schema 和实际注册的 callable 一一对应，避免评测时出现 schema 声明了但 callable 不存在的情况

### A5 · Config 集中配置 + 环境变量覆盖

- **源代码位置**：`ai_agent/config.py`
- **决策内容**：把散落在 client.py / rag.py / main.py 中的 base_url / model / embed_model / chunk_size / mcp_servers / skill_dir 等配置项集中到一个 frozen `Config` dataclass，所有值可通过环境变量覆盖，`Config.from_env()` 是唯一构造入口。
- **关键代码片段**：

```python
# config.py L24-L73
@dataclass(frozen=True)
class Config:
    base_url: str = "http://localhost:1234/v1"
    model: str = "auto"
    mcp_servers: tuple = ()          # 分号分隔字符串 → tuple
    mcp_allowed_tools: tuple = ()
    skill_dir: str = "skills"

    @classmethod
    def from_env(cls) -> Config:
        raw_mcp = os.environ.get("MCP_SERVERS", "").strip()
        servers = tuple(s.strip() for s in raw_mcp.split(";") if s.strip()) if raw_mcp else ()
        return cls(
            base_url=os.environ.get("LM_STUDIO_BASE_URL", cls.base_url),
            mcp_servers=servers,
            # ... 每个字段都有 env 覆盖
        )
```

- **设计意图**：消除硬编码，便于评测/CLI/Web UI 共享同一套配置；支持 `.env` 文件注入，降低不同部署环境的配置成本。
- **权衡分析**：
  - ✅ 好处：一处定义多处引用，环境变量覆盖让评测可以临时改配置而不改代码
  - ❌ 代价：frozen dataclass + tuple 类型，调试时在内存中看不到"哪些字段被 env 覆盖了"
  - 对比方案：用 Python 原生 `configparser` / YAML 配置文件——需要额外依赖，且 `.env` 文件已经足够覆盖需求
- **影响范围**：`main.py`、`web_ui.py`、`eval.py` 均通过 `cfg = Config.from_env()` 获取；client / rag / mcp_client 全部从 Config 取值
- **演进方向**：增加 `Config.validate()` 方法做启动时校验（如 `base_url` 必须有 http:// 前缀、`chunk_overlap < chunk_size`），把潜在错误提前暴露

## 二、安全与工具执行策略

### S1 · 按风险分类的安全执行器

- **源代码位置**：`ai_agent/tooling.py` → `ToolPolicy` / `ToolExecutor`
- **决策内容**：`ToolPolicy.classify(name)` 将工具分为 read / write / execute / mcp 四级；`ToolExecutor.execute()` 先分类，再判定当前 surface 是否允许，最后判定是否需要人工确认。
- **关键代码片段**：

```python
# tooling.py L13-L36 — 风险分类的核心逻辑
EXECUTE_TOOLS = frozenset({"run_code", "run_terminal", "demo_code_run"})
WRITE_TOOLS = frozenset({"file_write"})

class ToolPolicy:
    def classify(self, name: str) -> RiskKind:
        if name in EXECUTE_TOOLS: return "execute"
        if name in WRITE_TOOLS:   return "write"
        if name.startswith("mcp_"): return "mcp"
        return "read"

# tooling.py L81-L82 — execute 风险自动注入 allow_unsafe
if risk == "execute" and "allow_unsafe" in params:
    kwargs["allow_unsafe"] = True
```

- **设计意图**：同一套 tool_map 在不同 surface 有不同安全策略——Web UI 默认禁止 execute，CLI 允许但每次需确认。把安全逻辑从工具实现里抽离到统一执行器。
- **权衡分析**：
  - ✅ 好处：安全策略可声明式配置（一行 dataclass 字段切换整套行为），execute 风险自动注入 `allow_unsafe=True` 省掉每个工具重复判断
  - ❌ 代价：`classify()` 靠工具名匹配，新增 execute 工具必须同步加入 `EXECUTE_TOOLS` 集合，否则被误判为 read
  - 对比方案：让每个工具函数自己声明 risk（如 `@tool(risk="execute")` 装饰器）——但 Function Calling schema 里没有 risk 字段，要额外维护
- **影响范围**：所有工具调用都走 `ToolExecutor.execute()`；`build_tool_executor()` 在 CLI / Web UI / Eval 三处各有一套不同参数
- **演进方向**：让 schema 里增加自定义字段 `"x-risk": "execute"`，classify 从 schema 读取而不是靠工具名匹配，彻底消除"新增工具忘加集合"的风险

### S2 · AST 白名单计算器

- **源代码位置**：`ai_agent/tools/demo.py` → `calculator()` (L21-L67)
- **决策内容**：`calculator` 工具用 `ast.parse()` + 白名单节点递归验证表达式，拒绝 `Call` / `Name` / `Attribute` 等任何函数调用或变量引用，只允许常量 + 四则/幂/取模运算。
- **关键代码片段**：

```python
# tools/demo.py L29-L59 — AST 白名单的核心
_ALLOWED_OPS = {
    ast.Add: operator.add, ast.Sub: operator.sub,
    ast.Mult: operator.mul, ast.Div: operator.truediv,
    ast.Pow: operator.pow, ast.Mod: operator.mod,
    ast.USub: operator.neg,
}

def _safe_eval(node):
    if isinstance(node, ast.BinOp):
        if type(node.op) not in _ALLOWED_OPS:
            raise ValueError(f"不支持的运算符: {op_type.__name__}")
        # ... 递归 evaluate 左右子树
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value
    # Name / Call / Attribute / Subscript / Lambda — 一律拒绝
    raise ValueError(f"不支持的表达式元素: {type(node).__name__}")
```

- **设计意图**：比 try-except 更根本地阻断代码注入——`eval("__import__('os').listdir()")` 会在 AST 解析后遇到 `Call` 节点直接被拒，根本到不了执行阶段。
- **权衡分析**：
  - ✅ 好处：数学表达式安全边界绝对清晰，指数绝对值 >1000 额外防护防 DoS
  - ❌ 代价：`ast.Constant` 在 Python 3.7+ 才稳定支持，3.6 及以下是 `ast.Num` / `ast.Str`（本项目要求 Python 3.10+，无问题）
  - 对比方案：正则匹配 `[-+*/.()0-9 ]` 白名单——无法处理运算符优先级、括号嵌套、一元负号等，漏检风险大
- **影响范围**：LLM 生成的数学计算 prompt 会被路由到此工具；评测用例 `calculator_security_blocked` 覆盖此安全边界
- **演进方向**：支持变量（如 `a=5; a*2`）的话需要引入符号表，复杂度会显著上升；当前教学场景下保持纯表达式即可

### S3 · SQL Demo 模式阻断 DDL/DML

- **源代码位置**：`ai_agent/tools/sql.py` → `sql_query()` (L51-L80+)
- **决策内容**：SQLite 连接用 `mode=ro` URI 参数 + `PRAGMA query_only=ON` 双重只读保护，从数据库层物理阻断所有写入语句。
- **关键代码片段**：

```python
# tools/sql.py L75-L80 — 数据库层物理只读保护
sql_stripped = sql.strip().rstrip(";")
uri = abs_path.as_uri() + "?mode=ro"   # SQLite URI 参数：只读打开
conn = sqlite3.connect(uri, uri=True)
conn.row_factory = sqlite3.Row
conn.execute("PRAGMA query_only=ON")   # SQLite 3.8.0+ 才支持，进一步保险
```

- **设计意图**：让 SQL 演示安全可控——即使 LLM "不小心"生成了 `DROP TABLE users`，也会被 SQLite 引擎在执行层报错，不可能真正删除数据。
- **权衡分析**：
  - ✅ 好处：双重保护——URI mode=ro 是 OS 文件级只读，PRAGMA query_only 是 SQLite 引擎级只读，任意一个生效都够
  - ❌ 代价：不支持 `demo_seed=False` 让用户真的执行 DDL/DML（如建表练习），如果需要只能单独实现
  - 对比方案：正则匹配 SQL 开头（只允许 SELECT）——绕过方式多（如 `WITH cte AS (DELETE ...)`），防御不彻底
- **影响范围**：所有 SQL 查询都走此工具；评测用例 `sql_security_drop_blocked` 验证此边界；首次 demo_seed=True 建表在另一个独立 connect（非只读）中完成
- **演进方向**：如果需要支持 DDL/DML 执行练习，可新增 `sql_query_readwrite()` 工具，但要加 `human_confirm` 前置 + 操作日志

### S4 · PowerShell 危险命令关键词拦截

- **源代码位置**：`ai_agent/tools/system.py` → `_DANGEROUS_CMD_PATTERNS` (L50-L95+) + `run_terminal()` 内拦截逻辑
- **决策内容**：`_DANGEROUS_CMD_PATTERNS` 列出约 40 条高危子串（覆盖 Unix rm 系、Windows Remove-Item 系、写入命令、关机命令、fork bomb 等），run_terminal 执行前用 `re.search("|".join(_DANGEROUS_CMD_PATTERNS), cmd, re.IGNORECASE)` 匹配，命中则阻断。
- **关键代码片段**：

```python
# tools/system.py L48-L79
_DANGEROUS_CMD_PATTERNS = [
    # Unix 风格（跨平台）
    "rm -rf /", "rm -rf *", "rm -rf .", "rm -r /",
    # Windows / PowerShell 原生
    "Remove-Item -Recurse -Force", "Remove-Item -Recurse",
    "Remove-Item *", "Remove-Item",
    "Stop-Computer", "Restart-Computer",
    "Stop-Process -Force", "Format-Volume",
    "Set-Content", "Out-File", "Add-Content",
    "Invoke-WebRequest",
    # ... 共约 40 条
]
```

- **设计意图**：关键词拦截 + human_confirm + ToolExecutor.confirm_execute 形成三层保护——硬拦截（代码执行不到）、软拦截（LLM 主动调 human_confirm）、执行器拦截（CLI 每次 execute 风险都需确认）。
- **权衡分析**：
  - ✅ 好处：三层保护纵深防御；拦截列表是显式的，可审查可扩展
  - ❌ 代价：关键词拦截是黑名单思路，可以被绕过（如 `Remove-Item -Path "C:\*" -Force` 换个写法）；黑名单不可能穷举
  - 对比方案：白名单思路（只允许 `Get-*` / `Select-*` / `Test-*` 只读命令）——更安全但限制太死，教学场景下用户无法尝试任何写入类命令
- **影响范围**：run_terminal 和 run_code 两个 execute 类工具；ToolExecutor 的 confirm_execute 对 execute 风险做二次确认
- **演进方向**：引入 PowerShell AST 解析（`[System.Management.Automation.Language.Parser]::ParseInput`），真正理解命令意图，而不是靠子串匹配

### S5 · Human-in-the-loop 作为一等工具

- **源代码位置**：`ai_agent/app_core.py` → `human_confirm` schema (L218-L229) + `build_tool_map()` 注册；`ai_agent/web_ui.py` → `_web_human_confirm` 实现

## 三、RAG 知识库与数据层

### R1 · 本地 JSON 缓存 + 版本化 key

- **源代码位置**：`ai_agent/rag.py` → `_cache_key()` (L195-L206) / `_valid_cache()` (L217-L229) / `_write_cache()` (L231-L245) / `_load_cache()` (L208-L215)
- **决策内容**：向量化结果缓存到本地 JSON 文件，cache key 由 `CACHE_VERSION` / embed_model / chunk_size / chunk_overlap / 每个源文件的绝对路径 + stat.st_size + stat.st_mtime_ns 拼接而成。任何一个源文件修改或参数变化都会触发重新向量化。
- **关键代码片段**：

```python
# rag.py L195-L206 — cache key 的构成
def _cache_key(self, valid_paths: list[str]) -> str:
    parts = [str(self.CACHE_VERSION), self.embed_model, str(self.chunk_size), str(self.chunk_overlap)]
    for path in valid_paths:
        resolved = Path(path).resolve()
        stat = resolved.stat()
        parts.append(f"{resolved}:{stat.st_size}:{stat.st_mtime_ns}")
    return "|".join(parts)

# rag.py L217-L229 — 缓存有效性校验
def _valid_cache(self, cached, key: str) -> bool:
    return (cached.get("version") == self.CACHE_VERSION
            and cached.get("key") == key       # key 精确匹配（文件没变、参数没变）
            and len(cached.get("chunks", [])) > 0
            and len(cached.get("vectors", [])) == len(cached["chunks"]))
```

- **设计意图**：首次向量化耗时大（需要逐文件读 + 分块 + 批量调 embedding HTTP 接口，PDF 可能上百页），后续启动直接加载 JSON 缓存秒级恢复。`CACHE_VERSION=2` 用于格式升级时自动失效旧缓存（从 v1 的 list 格式升级到 v2 的 dict + key 格式时改过一次）。
- **权衡分析**：
  - ✅ 好处：零配置自动失效（改文件名/大小/mtime 都会触发重建）；版本号升级时旧缓存自动跳过；JSON 文件可被 gitignore 干净忽略
  - ❌ 代价：mtime 精度依赖文件系统（Windows ntfs 是 100ns 精度，FAT32 是 2 秒）；批量改文件名会导致全量重建
  - 对比方案：用文件 hash（SHA-256）做 key——更精确但每次启动都要读全文件算 hash，启动变慢；mtime + size 的组合已足够且启动无开销
- **影响范围**：CLI 启动自动构建 / 加载缓存；Web UI 同理；评测独立使用 tempdir 避免主项目缓存污染
- **演进方向**：支持增量更新——检测到只有一个文件变化时，只重向量化该文件的 chunks，从其他文件的缓存中保留未变部分

### R2 · 原子写入（tmp + os.replace）

- **源代码位置**：`ai_agent/rag.py` → `_write_cache()` (L231-L245)
- **决策内容**：缓存文件写入先写 `.tmp` 临时文件（`os.replace(cache_path.with_suffix(".tmp"), cache_path)`），确保目标文件要么完整存在要么完全不存在，不会出现半写状态。
- **关键代码片段**：

```python
# rag.py L231-L245
def _write_cache(self, key: str) -> None:
    cache_path = Path(self.cache_file)
    cache_path.parent.mkdir(parents=True, exist_ok=True)
    payload = {"version": self.CACHE_VERSION, "key": key,
               "chunks": self.chunks, "vectors": self.vectors,
               "sources": self.sources, "chunk_indices": self.chunk_indices}
    temp_path = cache_path.with_suffix(cache_path.suffix + ".tmp")
    with temp_path.open("w", encoding="utf-8") as f:
        json.dump(payload, f, ensure_ascii=False)
    os.replace(temp_path, cache_path)  # 原子替换
```

- **设计意图**：防止进程中断（Ctrl+C / 崩溃）导致留下半写文件。下次启动时 `_load_cache()` 会因 `json.JSONDecodeError` 读不到完整结构，但 `.tmp` 文件可能还残留——当前实现里 `_load_cache()` 只看主文件，`.tmp` 残留会在下次重建时被 `os.replace` 覆盖。
- **权衡分析**：
  - ✅ 好处：`os.replace` 在 Windows / macOS / Linux 上都是原子操作（目标存在先删后换，不存在则 rename）
  - ❌ 代价：`.tmp` 文件在崩溃后会残留（虽然不影响下次启动）；如果进程两次崩溃可能残留多份 `.tmp`
  - 对比方案：`os.rename`（非原子，跨盘 rename 可能失败）、`open("w")` 直接覆盖（崩溃时文件损坏）
- **影响范围**：仅 `_write_cache()` 一处；`_load_cache()` 是纯读，不涉及原子性问题
- **演进方向**：`_load_cache()` 读主文件失败时尝试读取最近的 `.tmp` 作为降级源；`write_cache` 前清理历史 `.tmp` 残留

### R3 · 手写余弦相似度 + 批量 embedding

- **源代码位置**：`ai_agent/rag.py` → `_cosine()` (L82-L86) / `_embed()` (L52-L59) / `build()` (L132-L138)
- **决策内容**：不引入 FAISS / chromaDB / Milvus 等向量库，用纯 Python `_cosine()` 实现余弦相似度；embedding 分批 16 条调用减少 HTTP 次数。
- **关键代码片段**：

```python
# rag.py L82-L86 — 手写余弦相似度
def _cosine(self, a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    na = sum(x * x for x in a) ** 0.5
    nb = sum(x * x for x in b) ** 0.5
    return dot / (na * nb) if na and nb else 0.0

# rag.py L132-L138 — 批量 embedding
batch_size = 16
for start in range(0, len(self.chunks), batch_size):
    self.vectors.extend(self._embed(self.chunks[start : start + batch_size]))
```

- **设计意图**：教学项目无需重量级向量库，简单实现足够演示"分块→向量化→检索→问答"的完整 RAG 链路。批量调用是因为 LM Studio 的 `/embeddings` endpoint 支持批量，16 条比单条 16 次 HTTP 调用快 ~10x。
- **权衡分析**：
  - ✅ 好处：零新增依赖、代码可读可教；cosine + 线性扫描对几百条 chunk 来说（项目当前 ~500 chunks）< 1ms，完全够用
  - ❌ 代价：线性扫描 O(N) 不扩展，chunk 超过 10000 条时才需要 FAISS；批量 16 条是硬编码，没根据服务端能力自适应
  - 对比方案：引入 chromaDB / FAISS——`pip install faiss-cpu` 体积大（~20MB），且对教学项目来说是不必要的复杂度
- **影响范围**：`search()` / `search_detailed()` / `answer()` 所有检索入口
- **演进方向**：chunk 数量 < 2000 保持手写 cosine；达到阈值后自动切换 FAISS IndexFlatIP（内积等价于 cosine，且 FAISS GPU 可用）

### R4 · 多编码自动探测

- **源代码位置**：`ai_agent/rag.py` → `_extract_text()` (L61-L80)
- **决策内容**：文件读取按 utf-8 → utf-8-sig → gbk → latin-1 顺序尝试，遇到 `UnicodeDecodeError` 继续尝试下一种编码。
- **关键代码片段**：

```python
# rag.py L72-L79
if ext in (".md", ".txt"):
    for enc in ("utf-8", "utf-8-sig", "gbk", "latin-1"):
        try:
            with open(path, encoding=enc) as f:
                return f.read()
        except UnicodeDecodeError:
            continue
    raise RuntimeError(f"无法识别文件 {path} 的编码")
```

- **设计意图**：Windows 中文环境下 GBK 编码常见（企业内部文档、老项目文件），单一 utf-8 会导致 `pypdf.PdfReader.extract_text()` 返回空字符串、`.md` 文件读到乱码。多编码探测保证了在 Windows 中文路径下的健壮性。
- **权衡分析**：
  - ✅ 好处：用户放进来的任意中文 md/txt 文件都能读，零配置
  - ❌ 代价：latin-1 是"永远不会报错"的兜底，可能把非 latin-1 文件读成乱码但不抛异常；静默成功的乱码比显式报错更难排查
  - 对比方案：用 `chardet` 自动检测编码——需要额外依赖（`pip install chardet`），且检测结果不一定准
- **影响范围**：`build()` 方法读源文件时调用；PDF 走 `pypdf.PdfReader`（自己处理编码），不受此决策影响
- **演进方向**：探测到 latin-1 兜底成功时打印 warning，提示用户文件编码可能有问题；或在 GBK 成功时标记 encoding="gbk" 存入 cache，下次跳过探测直接用 GBK

```python
_FM_RE = re.compile(r"^---\s*\n(.*?)\n---\s*\n(.*)$", re.DOTALL)

def _parse_frontmatter(fm_text: str) -> dict:
    result = {}
    for line in fm_text.split("\n"):
        key_match = re.match(r"^([a-zA-Z_]\w*)\s*:\s*$", line)
        if key_match:
            # 裸列表：key:\n  - item1\n  - item2
            key = key_match.group(1)
            items = []
            # ... 收集缩进 + - 开头的行
            result[key] = items
            continue
        kv_match = re.match(r"^([a-zA-Z_]\w*)\s*:\s*(.*)$", line)
        # 内联值 / 内联列表 [a, b, c]
    return result
```

- **设计意图**：Skill 是 Tool 的上层抽象——场景化 Prompt + 工具子集过滤 + 多轮执行循环。纯文本定义让非开发者也能编写 Skill，无需改代码。刻意不支持 PyYAML 的嵌套字典 / 多行字符串，因为 Skill 元数据用不到。
- **权衡分析**：
  - ✅ 好处：零额外依赖（PyYAML ~2MB）；正则解析性能极佳；Skill 文件可以直接在 VSCode / Obsidian 里编辑预览
  - ❌ 代价：YAML 子集有限，遇到嵌套需求时必须升级；`_parse_frontmatter` 的"裸列表"分支（缩进 + "- xxx"）解析复杂
  - 对比方案：引入 PyYAML——功能全但体积大，且需要处理 PyYAML 的安全 loader（`yaml.safe_load` vs `yaml.load`）
- **影响范围**：`SkillRegistry` 加载 `skills/*.md` 时调用；`AgentRuntime.run()` 通过 `skill_registry.match()` 路由；system prompt 动态合成时引用 skill 列表简述
- **演进方向**：如果未来 Skill 元数据需要嵌套（如 `required_tools_by_role: {planner: [tool1], executor: [tool2]}`），升级为 PyYAML；但目前 Skill 结构已足够简单，升级会增加维护成本

### K2 · 关键词预筛路由算法

- **源代码位置**：`ai_agent/skill.py` → `SkillRegistry.match()` (L266-L315)
- **决策内容**：对每个 Skill 的 `trigger_keywords` 做子串匹配（不区分大小写），计算 `score = 命中关键词覆盖字符数 / 用户输入长度`，附加多关键词同时命中 × 1.3 奖励系数，score > 0.3 才算有效命中，取最高分 Skill。
- **关键代码片段**：

```python
# skill.py L285-L314 — 匹配核心算法
for skill in self.skills.values():
    matched_keywords = [kw for kw in skill.trigger_keywords
                        if kw and kw.lower() in user_lower]
    covered_positions: set[int] = set()
    for keyword in matched_keywords:
        start = 0
        while True:
            found = user_lower.find(keyword, start)
            if found < 0: break
            covered_positions.update(range(found, found + len(keyword)))
            start = found + 1
    hit_chars = len(covered_positions)
    score = hit_chars / input_len
    hit_count = len(set(matched_keywords))
    if hit_count >= 2:
        score *= 1.3
    if score > best_score and score > 0.3:
        best_score = score
        best_skill = skill
```

- **设计意图**：比 LLM meta-routing 简单可靠、零额外 token 开销。阈值 0.3 防止单字/短关键词误触——"规划" 两个字在 50 字输入中占比 4%，过不了阈值；"帮我规划一下"（5 个字符覆盖）在 50 字输入中占比 10%，多个关键词叠加才够 0.3。
- **权衡分析**：
  - ✅ 好处：速度微秒级；可解释（打印 score 就能看到命中了哪些关键词）；阈值可调
  - ❌ 代价：纯字符串匹配无法处理语义（"用 planner 帮我写文章"和"用规划帮我写文章"关键词覆盖完全不同）；阈值 0.3 是拍脑袋的经验值
  - 对比方案：LLM meta-routing——让 LLM 从候选 Skill 列表里选，精准但每次多一次 API 调用（多一次 HTTP 往返）
- **影响范围**：`AgentRuntime.run()` 每次都会调 `skill_registry.match(last_user)`，命中后走 Skill 执行路径；CLI / Web UI 共享同一套路由
- **演进方向**：注释里已标注"后面可以升级为 LLM meta-routing"——先做关键词预筛拿候选 Top-3，再让 LLM 从 Top-3 里选（降低 LLM 决策空间，减少 token 开销）

### K3 · Skill 激活时 system prompt 替换 + 工具集收窄

- **源代码位置**：`ai_agent/runtime.py` → `run()` (L56-L67) / `_apply_skill_prompt()` (L172-L183)
- **决策内容**：Skill 一旦被 match 命中，用 Skill 的 `instructions` 完全替换原 system prompt，同时过滤 tool_map 只保留 `required_tools` 声明的工具，max_iterations 覆盖为 `skill.max_rounds`。history 用 `list(messages)` 复制，不修改外部传入。
- **关键代码片段**：

```python
# runtime.py L58-L67 — Skill 激活的完整效果链
if selected_skill is not None:
    history = self._apply_skill_prompt(history, selected_skill.instructions)  # 替换 system
    required = set(selected_skill.required_tools)
    active_map = {name: fn for name, fn in tool_map.items()
                  if not required or name in required}                        # 收窄工具集
    active_tools = [schema for schema in get_tool_schemas(mcp_manager)
                    if schema["function"]["name"] in active_map]
    max_iterations = selected_skill.max_rounds                               # 覆盖迭代上限

# runtime.py L172-L183 — system prompt 替换（只替换第一个 system）
def _apply_skill_prompt(messages, instructions):
    result = []
    replaced = False
    for message in messages:
        if message.get("role") == "system" and not replaced:
            result.append({"role": "system", "content": instructions})
            replaced = True
        else:
            result.append(message)
    if not replaced:
        result.insert(0, {"role": "system", "content": instructions})
    return result
```

- **设计意图**：Skill 激活期间形成完全隔离的执行空间——原有的通用路由 prompt 和完整工具集被 Skill 的场景化 prompt + 专用工具集完全覆盖，避免通用 prompt 干扰 Skill 的专业化行为。
- **权衡分析**：
  - ✅ 好处：Skill 执行行为可预测（只有声明的工具可用、只有声明的 prompt 生效）；history 复制保证多次 Skill 激活不会互相污染
  - ❌ 代价：替换是破坏性的——原来 system prompt 里关于安全的指引（如 human_confirm）不会自动继承到 Skill prompt 里，必须在 Skill 的 instructions 里自己写一遍
  - 对比方案：把 Skill prompt 追加到原 system prompt 后面（`原 prompt + Skill prompt`）——可能相互冲突，且 Skill prompt 应该是完全的领域专家身份，不是通用助手 + 专项补丁
- **影响范围**：AgentRuntime 是唯一执行入口；CLI / Web UI 都走 AgentRuntime；Skill 的 `required_tools` 如果声明了不存在的工具，`build_tool_map` 会给 warning 但不会报错
- **演进方向**：让 Skill instructions 里可以用占位符 `{{base_safety_rules}}` 引用安全基线，自动注入 human_confirm / SQL 安全边界等通用规则

### K4 · 多 Agent 三角色独立 messages 状态

- **源代码位置**：`ai_agent/multi_agent.py` → `run_multi_agent()` 全文
- **决策内容**：Planner / Executor / Critic 三个角色各自维护独立的 messages 列表，不共享主 Agent 的 history。每个角色有独立 System Prompt（`ROLE_PROMPTS["planner"]` / `["executor"]` / `["critic"]`）体现角色人格。
- **关键代码片段**：

```python
# multi_agent.py L162-L168 — Planner 独立 messages
planner_msgs = [
    {"role": "system", "content": ROLE_PROMPTS["planner"]},
    {"role": "user", "content": f"请为下面的任务制定执行计划：\n\n{user_task}"},
]
plan_text = client.chat(planner_msgs, ...)

# multi_agent.py L230-L242 — Executor 独立 messages（只含自己的 system + 当前子任务上下文）
executor_msgs = [
    {"role": "system", "content": ROLE_PROMPTS["executor"]},
    {"role": "user", "content": f"整体任务回顾：{user_task}...当前子任务：{i}. {subtask}..."},
]
exec_output = client.chat(executor_msgs, ...)
```

- **设计意图**：每个角色的 messages 列表只包含自己的 system prompt + 收到的任务/前序产出，避免跨角色上下文污染（比如 Planner 的规划过程不会暴露给 Executor，Executor 不需要知道 Planner 是怎么想的）。角色间通过 `trace_callback` 传回进度文本而非共享状态——这是显式消息传递（Message Passing）的实现。
- **权衡分析**：
  - ✅ 好处：角色边界清晰；每个角色可以调用不同的 LLM（当前共用同一个 client 但 messages 独立）；trace_callback 是单向信息流（Agent → 外部），不形成反向依赖
  - ❌ 代价：Executor 看不到 Planner 的完整规划过程（只看最终 plan_text），如果 Planner 规划有缺陷，Executor 也无法修正
  - 对比方案：所有角色共享同一条 history——会导致身份混乱（Critic 看到自己的前几轮批评 + Executor 的修正 + Planner 的原始计划），且无法让每个角色有独立 system prompt
- **影响范围**：`run_multi_agent` 被注册为 Function Calling 工具 `run_multi_agent`，可被 LLM 路由触发；CLI / Web UI / Eval 共享同一个函数
- **演进方向**：让角色间有显式的消息通道——比如 Executor 可以向 Planner 发"你这个子任务我做不了"，Planner 动态调整计划（当前是静态 plan → Executor 逐个执行）

### K5 · Critic 不通过时循环重试

- **源代码位置**：`ai_agent/multi_agent.py` → (L179-L220) 规划阶段循环 / (L245-L282) 执行阶段循环
- **决策内容**：规划阶段和执行阶段各自独立的 Critic 评审循环——Critic 不通过时，把批评意见追加到 Planner/Executor 的 messages 末尾，让 LLM 带着批评意见重规划/修正，最多 `max_rounds` 轮。
- **关键代码片段**：

```python
# multi_agent.py L179-L220 — Planner 规划的 Critic 循环
for round_num in range(1, max_rounds + 1):
    critic_reply = client.chat(critic_msgs, ...)
    if _parse_critic_decision(critic_reply):
        break                                    # ✅ 通过了
    # ❌ 不通过：让 Planner 带着批评意见重规划
    planner_msgs = [
        {"role": "system", "content": ROLE_PROMPTS["planner"]},
        {"role": "user", "content": f"任务：{user_task}"},
        {"role": "assistant", "content": plan_text},     # 之前的计划
        {"role": "user", "content": critic_reply},       # 批评意见
    ]
    plan_text = client.chat(planner_msgs, ...)          # 重新生成
```

- **设计意图**：教学演示——让学习者看到"评审→修正→再评审"的质量闭环是如何在代码中实现的。不是硬编码重试次数，而是每一轮都调用 LLM 让它真正反思批评意见。max_rounds 耗尽后仍不通过，打印警告但按当前产出继续推进（避免卡死循环）。
- **权衡分析**：
  - ✅ 好处：每一轮重试的 messages 都包含"原始输入 + 之前的失败产出 + Critic 的批评意见"，LLM 有足够上下文针对性修正
  - ❌ 代价：每一轮多两次 API 调用（Critic 评审 + Planner/Executor 修正），成本线性增加；`_parse_critic_decision` 靠 emoji 标记（✅ / ❌），LLM 偶尔会忘加 emoji 导致解析失败
  - 对比方案：Critic 不通过时直接返回最终产出（不重试）——教学意义弱，无法展示质量闭环
- **影响范围**：`run_multi_agent` 内部两阶段都有循环；`max_rounds` 默认 2 轮（CLI 传参可调）
- **演进方向**：`_parse_critic_decision` 增加关键词匹配（"通过" / "不通过" 中文也能识别）；或让 Critic 输出结构化 JSON（`{"decision": "pass/reject", "reason": "..."}`），解析更可靠

### P1 · 极简 MCP Streamable HTTP 客户端

- **源代码位置**：`ai_agent/mcp_client.py` → `MCPClient` / `MCPManager`
- **决策内容**：只依赖项目已有的 `requests` 库实现 MCP Streamable HTTP Transport（POST JSON-RPC 请求），不支持 STDIO / SSE（需要子进程或特殊流处理）。`MCPManager` 聚合多个 server 的工具，统一转成 OpenAI function schema 格式。
- **关键代码片段**：

```python
# mcp_client.py L99-L154 — 核心 JSON-RPC 请求/响应
def _send(self, method: str, params: dict | None = None) -> Any:
    payload = {"jsonrpc": "2.0", "id": self._request_id,
               "method": method, "params": params or {}}
    hdrs = dict(self.headers)
    if self._session_id:
        hdrs["Mcp-Session-Id"] = self._session_id
    if self.protocol_version:
        hdrs["Mcp-Protocol-Version"] = self.protocol_version
    resp = requests.post(self.url, data=json.dumps(payload), headers=hdrs, timeout=self.timeout)
    # ... 解析响应、提取 session_id、处理 error
```

- **设计意图**：零外部新增依赖；MCP 客户端实现 keep 精简，覆盖最主流的 Streamable HTTP 协议即可满足教学需求。注释里明确标注后续可扩展 STDIO/SSE。
- **权衡分析**：
  - ✅ 好处：不用 `pip install mcp`（官方 SDK 体积大 + 依赖复杂）；Streamable HTTP 是官方推荐的"Web-first"传输
  - ❌ 代价：STDIO Transport（MCP 最常见的本地工具方式）不支持——需要子进程 + stdin/stdout 读写，requests 做不到
  - 对比方案：引入官方 `mcp` SDK——2025 年 6 月刚发布，API 还不稳定；且 SDK 会引入 asyncio + pydantic 等额外依赖
- **影响范围**：Web UI 启动时调用 `create_mcp_manager()` 聚合远端工具；CLI 默认不启用 MCP（env 未配置时 `mcp_servers` 为空 tuple）
- **演进方向**：新增 `MCPClientSTDIO`（子进程 + Popen communicate），支持本地 MCP server（如 Desktop Commander、Filesystem 等）；同时 MCPManager 支持混合 Transport 聚合

### P2 · MCP 工具纳入统一安全策略

- **源代码位置**：`ai_agent/tooling.py` → `ToolPolicy.classify()` / `_denial_reason()` (L29-L35)
- **决策内容**：`ToolPolicy.classify()` 用 `name.startswith("mcp_")` 自动识别 MCP 工具，归入 "mcp" 风险等级；`mcp_allowlist` 白名单精确控制允许哪些 MCP 工具。
- **关键代码片段**：

```python
# tooling.py L29-L35
def classify(self, name: str) -> RiskKind:
    if name in EXECUTE_TOOLS: return "execute"
    if name in WRITE_TOOLS:   return "write"
    if name.startswith("mcp_"): return "mcp"          # ← MCP 工具自动识别
    return "read"

# tooling.py L95-L101 — MCP 风险的拒绝逻辑
if risk == "mcp":
    if not self.policy.allow_mcp:
        return f"安全限制：当前模式禁止 MCP 工具 {name}"
    if allowlist is not None and name not in allowlist:
        return f"安全限制：MCP 工具 {name} 不在允许列表中"
```

- **设计意图**：把 MCP 远端工具纳入与本地工具相同的安全策略体系，不是"开了 MCP 就全开"。Web UI 下 `allow_mcp = bool(mcp_allowed_tools) and not disable_dangerous`，默认关闭，必须显式配置 `MCP_ALLOWED_TOOLS=xxx;yyy` 才启用。
- **权衡分析**：
  - ✅ 好处：ToolPolicy 的四分类模型天然容纳了远端工具——只需加一个前缀判断；allowlist 让用户可以只开启 MCP server 的一部分工具（如开 filesystem 不开 terminal）
  - ❌ 代价：`startswith("mcp_")` 是约定式识别——如果有人自己写了一个本地工具叫 `mcp_backup`（不是真 MCP 远端），会被误判为 MCP 类型
  - 对比方案：让 MCPManager 在生成 callable 时统一加风险标记（如 closure 的 `__risk__ = "mcp"`）——更精确但需要改 ToolExecutor 的 classify 逻辑从 callable 读取 risk 属性
- **影响范围**：所有 MCP 工具调用都走此分类；CLI / Web UI / Eval 三处的 ToolExecutor 构造参数各自不同（CLI 确认 MCP、Web UI 默认禁用、Eval 直接关闭）
- **演进方向**：用 `callable.__wrapped_by__ = "mcp"` 标记替代前缀匹配；或在 MCPManager.build_tool_callables() 里为每个生成的 closure 添加元属性

### P3 · MCP 工具名前缀 + 冲突解决

- **源代码位置**：`ai_agent/mcp_client.py` → `MCPManager.connect_all()` (L322-L346)
- **决策内容**：MCPManager 把远端工具名清洗（`re.sub(r"[^a-zA-Z0-9_]", "_", t.name)`）后加 server 索引前缀 `mcp_{idx}_{safe_name}`，若不同 server 有同名工具则后缀递增 `_{suffix}`。
- **关键代码片段**：

```python
# mcp_client.py L331-L337
for t in tools:
    safe_name = re.sub(r"[^a-zA-Z0-9_]", "_", t.name)
    final_name = f"mcp_{idx}_{safe_name}"
    suffix = 2
    while final_name in self._tool_names:        # 冲突解决
        final_name = f"mcp_{idx}_{safe_name}_{suffix}"
        suffix += 1
    self._tool_names[final_name] = (idx, t.name)
    t.server_index = idx
    t.name = final_name
```

- **设计意图**：多 server 聚合时工具名不能冲突，否则 LLM 返回的 `tool_call.name` 无法路由到正确的远端 server。前缀方案同时让本地 vs MCP 工具一眼可辨（本地工具无前缀，MCP 工具一定以 `mcp_` 开头）。
- **权衡分析**：
  - ✅ 好处：server 索引前缀让多个 server 的同名工具自然区分（如 `mcp_0_query` vs `mcp_1_query`）；后缀递增处理单 server 内重名的罕见情况
  - ❌ 代价：清洗规则（只保留字母数字下划线）可能丢失语义（如 `git-log` 变成 `git_log`），但 MCP 官方工具名都只包含合法字符
  - 对比方案：用 `server_url_hash_toolname` 做 key——不可读，调试时看不出这是哪个 server 的哪个工具
- **影响范围**：MCPManager 构建 tool_map / tool_schemas 时；ToolPolicy 的 `startswith("mcp_")` 依赖这个前缀
- **演进方向**：MCPTool dataclass 里增加 `final_name` / `original_name` / `server_idx` 字段，让 UI 层可以展示友好名称而不是技术前缀名

### P4 · 结构化输出失败重试

- **源代码位置**：`ai_agent/client.py` → `structured_extract()` (L666-L703)
- **决策内容**：首次 `_generate()` + `_parse()` 尝试生成合法 JSON；若 JSONDecodeError，追加"严格只输出 JSON"强化提示再重试一次。JSON 围栏（```json...```）会被 `re.sub(r"^```(?:json)?\s*|\s*```$", "", content, flags=re.MULTILINE)` 正则清洗掉。
- **关键代码片段**：

```python
# client.py L677-L701
def _generate(extra_hint: str = "") -> str:
    return client.chat.completions.create(..., messages=[{"role": "user", "content": prompt + extra_hint}])

def _parse(content: str) -> dict:
    content = content.strip()
    content = re.sub(r"^```(?:json)?\s*|\s*```$", "", content, flags=re.MULTILINE)  # 清洗 markdown 围栏
    return json.loads(content)

raw = _generate()
try:
    data = _parse(raw)
except json.JSONDecodeError:
    raw = _generate('\n\n上一次输出不是合法 JSON，这次请**严格只输出** {"字段1": 值1, ...} 格式')
    data = _parse(raw)
```

- **设计意图**：LLM 偶尔会输出 markdown 围栏包裹或带解释文字的"准 JSON"。二次 prompt 提示让它收敛到纯 JSON——对教学项目来说重试一次成本可控，比实现更复杂的 JSON 修复器（从解释文字里提取 JSON 片段）更简单。
- **权衡分析**：
  - ✅ 好处：代码量小，两阶段简单直观；prompt 强化让 LLM 真正"明白问题并修正"
  - ❌ 代价：重试一次如果还失败就直接抛异常（当前没做第二次重试）；JSON 围栏清洗正则不处理围栏内外有文字的情况（如"下面是 JSON：```json...``` 好了"）
  - 对比方案：实现 JSON 修复器——用正则从任意文本里提取第一个完整 `{...}` 或 `[...]` 片段，再尝试 parse；更健壮但代码复杂度高
- **影响范围**：`extract_structured` 工具；EvalCase `structured_extract_basic`
- **演进方向**：增加二次重试 + JSON 片段提取——如果两次都 JSONDecodeError，用正则 `r"\{.*\}"` 贪婪匹配找第一个 JSON 对象尝试 parse

### P5 · 模型加载状态缓存

- **源代码位置**：`ai_agent/client.py` → `LMStudioClient._model_cached_name` (L47) / `ensure_model_loaded()` (L102-L118)
- **决策内容**：首次 `ensure_model_loaded()` 会 HTTP 调 `/models` 检查服务状态 + 模型加载情况，成功后把 `model_name` 缓存到 `_model_cached_name`，后续调用直接返回缓存值。`_model_checked` 标志只在首次成功时打印一次日志。
- **关键代码片段**：

```python
# client.py L46-L47 + L102-L118
class LMStudioClient:
    _model_checked = False             # 只在首次调用时打印状态
    _model_cached_name = None          # 首次成功后缓存，跳过后续 HTTP 检查

    def ensure_model_loaded(self) -> str:
        if self._model_cached_name is not None:
            return self._model_cached_name          # ← 缓存命中，零 HTTP
        status = self.check_server_status()          # ← 首次：HTTP /models
        if not status["server_running"]:
            raise RuntimeError(status["error"])
        if not status["model_loaded"]:
            raise RuntimeError(status["error"])
        self._model_cached_name = status["model_name"]  # ← 缓存
        return status["model_name"]
```

- **设计意图**：每次 LLM 请求前都调 `/models` 是浪费（HTTP 往返 + LM Studio 服务开销 ~100ms/次），且模型加载状态在单次运行期间通常不变。只首次检查，后续假设不变。
- **权衡分析**：
  - ✅ 好处：第二次及后续 `chat()` 调用跳过 `/models` 检查，每次省 ~100ms + 一个 LM Studio 服务请求；`_model_checked` 避免重复日志刷屏
  - ❌ 代价：运行中模型被卸载/切换时缓存值过期——但本项目是本地演示，这种情况极罕见；`check_server_status()` 里对 "auto" 模式做了特殊处理（取第一个 chat model）
  - 对比方案：每次都调 `/models`——可靠但浪费；用后台线程定时 poll——增加复杂度
- **影响范围**：所有 LLM API 调用（chat / chat_stream / chat_with_tools / summarize_messages / structured_extract 等）都会经过 `ensure_model_loaded()`
- **演进方向**：加一个 `invalidate_model_cache()` 公开方法，当检测到 LM Studio 服务端变化（如 `/models` 返回和缓存不一致）时主动失效；或让 cache 有 TTL（30 分钟后自动失效重新检查）

### U1 · Typed Event 迭代器 + on_event 回调

```python
yield emit("route_selected", {"mode": "skill" if selected_skill else "tools", ...})
```

- **设计意图**：AgentRuntime 只负责执行逻辑 + 产出类型化事件，不关心 UI 如何展示。CLI 打印文本（`[Tool Call] xxx` / `[Tool Result:OK] xxx`），Web UI 推 Gradio queue 做实时 trace 展示。两者消费同一个迭代器，各自格式化输出。
- **权衡分析**：
  - ✅ 好处：迭代器模式让"执行"和"渲染"彻底解耦；`AgentEvent` 是 frozen 不可变，CLI/Web UI 可以安全异步处理；sequence 自增保证顺序
  - ❌ 代价：callback 模式的 `on_event(event)` 里如果抛异常会中断 AgentRuntime 迭代（当前没做 try-except 包装）；CLI 的 on_event 是同步调用（`print`），如果改成 UI 需要异步
  - 对比方案：AgentRuntime 返回 List[AgentEvent]——简单但无法流式渲染（等所有事件产出完才能展示）；AsyncGenerator 更复杂
- **影响范围**：CLI `_on_agent_event` 回调（`main.py#L200-L208`）；Web UI 类似；AgentRuntime.run() 是唯一事件产出源
- **演进方向**：AgentRuntime 捕获 on_event callback 的异常并记录日志（不中断迭代）；支持 AsyncGenerator 让 Web UI 做真正的异步流式渲染

### U2 · Gradio per-browser State + threading.local

- **源代码位置**：`ai_agent/web_ui.py` → `AgentApp._state_local` (L64) / `_get_active_history()` (L119) / `_set_active_history()` (L122)
- **决策内容**：Web UI 用 Gradio State 组件做前端 per-tab 的 history 隔离；用 `threading.local()` 让 `summarize_history` 工具访问"当前线程的 history"——因为 Web UI 下 tool 执行发生在 Gradio 回调线程里。
- **关键代码片段**：

```python
# web_ui.py L64 — per-thread state 容器
self._state_local = threading.local()

# web_ui.py L119-L123 — 访问器（给 build_tool_map 的 set_history 参数）
def _get_active_history(self):
    return getattr(self._state_local, "history", [])

def _set_active_history(self, history) -> None:
    self._state_local.history = history
```

- **设计意图**：所有浏览器标签页共享同一个 `AgentApp` 实例（tool_map、rag、store 等初始化成本高），必须做 per-session 隔离。Gradio State 组件随每个请求传入/传出（`gr.State(new_state)`），threading.local 解决工具闭包无法直接访问"当前"history 的问题——`summarize_history` 工具在执行时需要读写 history，但它被注册在共享的 tool_map 上。
- **权衡分析**：
  - ✅ 好处：threading.local 让同一份 tool_map 在不同线程里访问不同的 history——零侵入；Gradio State 组件是框架原生支持
  - ❌ 代价：threading.local 在线程池复用时可能残留脏数据（Gradio 每个请求通常在独立线程，但线程池复用时要注意清理）；没有显式清理时机（当前没有手动 pop history 的逻辑）
  - 对比方案：每次请求创建新的 AgentApp 实例——初始化成本高（重新 load RAG / 重新注册 tools）；用 Flask 的 `g` 对象——概念上类似但依赖 Flask
- **影响范围**：Web UI 的 chat / clear / new_session 等所有回调都操作 State；build_tool_map 时传入 `get_history=self._get_active_history, set_history=self._set_active_history`
- **演进方向**：在每个 Gradio 回调开头显式 `setattr(self._state_local, "history", state["history"])` 初始化，回调结尾显式清理或保存回 State

- **设计意图**：纯文本对话架构没有窗口管理机制，只能靠定期摘要压防 token 溢出。保留最近消息 + 摘要的策略既节省 token 又保留最近上下文的完整性。
- **权衡分析**：
  - ✅ 好处：阈值触发完全自动；边界对齐保证截断点不会落在 assistant 回复中间；DB 重写保证持久化层和内存状态一致

- **演进方向**：阈值根据 `model` 动态调整（context window 的 70%）；让摘要保留结构化的关键事实（如"已完成任务 X"、"用户 Y 的偏好"），用 JSON 格式存储摘要

### T1 · Gold Case 评测集框架（多维度断言）

- **源代码位置**：`ai_agent/eval.py` → `EvalCase` (L38-L54) / `Evaluator._evaluate_one()` (L337-L431)
- **决策内容**：`EvalCase` 支持 6 维断言——`expected_tool`（主工具路由）、`expected_tools_called`（完整调用序列，顺序敏感）、`expected_contains`（输出关键词）、`expected_not_contains`（排除关键词）、`expected_tool_output_contains`（工具返回值关键词）、`expected_min_len`（最少字符数）。当前评测集覆盖 12 个 capability 标签。
- **关键代码片段**：

```python
# eval.py L379-L419 — 六维评分逻辑（节选）
failures: list[str] = []

# 1. 路由检查
if case.expected_tool is not None:
    if not tracker.calls:
        failures.append(f"预期调用 {case.expected_tool}，但未调用任何工具")
    elif case.expected_tool not in tracker.calls:
        failures.append(f"预期 {case.expected_tool}，实际: {' → '.join(tracker.calls)}")

# 2. 调用序列检查（顺序敏感）
if case.expected_tools_called:
    actual = tracker.calls[:]
    expected = case.expected_tools_called
    if actual[:len(expected)] != expected:
        failures.append(f"预期序列 {expected}，实际 {actual}")

# 3+4+5+6: 输出检查
for kw in case.expected_contains:
    if kw not in (output or ""):
        failures.append(f"输出应包含 '{kw}'")
```

- **设计意图**：比单一 pass/fail 细粒度多——能精确定位是路由错了（expected_tool 检查失败）、还是调用顺序错了（expected_tools_called 检查失败）、还是安全边界未生效（expected_not_contains 检查失败）。便于快速定位问题根因。
- **权衡分析**：
  - ✅ 好处：六维断言可组合；`expected_tools_called` 的"前缀匹配"（`actual[:len(expected)]`）设计允许用例只关心前几步，不强制全部调用序列；安全测试用 expected_not_contains 比 expected_contains 更有意义
  - ❌ 代价：`expected_tool=None` 的语义有两层——"不应调用任何工具" vs "不关心调用什么工具"，当前设计用额外的 expected_not_contains 来区分，不够清晰
  - 对比方案：用 LLM 做 evaluator（让 LLM 判断"回答是否正确"）——灵活但不稳定、成本高；正则匹配 + 关键词是 deterministic 的，可重复
- **影响范围**：`EVAL_CASES` 列表（20+ 条用例）；`Evaluator.run()` 和 HTML 报告生成；CI 可以 `python -m ai_agent.eval && exit $?`
- **演进方向**：增加 `expected_tool_calls_json` 维度——验证工具调用的参数是否正确（不只是工具名对）；让 `expected_tool=None` 有显式字段 `must_not_call_tools: bool`

### T2 · ToolCallTracker 装饰器包装

- **源代码位置**：`ai_agent/eval.py` → `ToolCallTracker` (L251-L281)
- **决策内容**：评测前用 wrapper 模式包装 tool_map 中每个工具，记录调用序列到 `tracker.calls`、调用结果到 `tracker.results`。`build_tracked()` 返回新 dict，原始 tool_map 不受影响。
- **关键代码片段**：

```python
# eval.py L259-L276
def build_tracked(self) -> dict:
    tracked = {}
    for name, func in self.original.items():
        tracked[name] = self._wrap(name, func)   # 包装每个工具
    return tracked

def _wrap(self, name: str, func: Callable) -> Callable:
    @wraps(func)
    def wrapper(*args, **kwargs):
        self.calls.append(name)                  # 记录调用序列
        result = func(*args, **kwargs)
        self.results.append((name, result if isinstance(result, str) else str(result)))
        return result                             # 原始结果原样返回
    return wrapper
```

- **设计意图**：零侵入式获取调用轨迹——不修改 tool_map 本体、不修改工具实现本身、不影响正常执行逻辑，只是在每次调用前后追加记录。`@wraps(func)` 保留原函数的 `__name__` / `__doc__`，Function Calling 层能正常工作。
- **权衡分析**：
  - ✅ 好处：`build_tracked()` 返回的 dict 可以安全传给 `ToolExecutor`（evaluator 里也会重建 executor 用 tracked_map）；原始 tool_map 可以被多个评测 case 复用
  - ❌ 代价：如果工具内部有状态（如 `file_read` 首次调用会读文件、第二次读缓存），包装不会影响行为——但如果工具抛异常，`tracker.calls` 里不会记录（异常时 wrapper 不会 append result）
  - 对比方案：让 AgentRuntime 自己记录 tool_call 序列——需要改 AgentRuntime 加 tracker 参数，增加耦合
- **影响范围**：仅 `Evaluator._evaluate_one()` 使用；正常 CLI/Web UI 流程不创建 ToolCallTracker
- **演进方向**：wrapper 里加 try-except——即使工具抛异常也能记录到 `tracker.errors.append((name, exc))`，评测时可以断言"某次工具调用应该抛异常"

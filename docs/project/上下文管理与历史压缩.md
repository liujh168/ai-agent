# 上下文管理与历史压缩

> 以本项目（AI Agent 交互式演示，基于 LM Studio 本地大模型）为实例，拆解长对话"为什么会爆上下文"、字符阈值如何触发压缩、摘要+边界对齐+SQLite 重写如何协同，以及 CLI 与 Web 如何共用同一套压缩逻辑。所有代码引用均可按 `文件:行号` 定位核实。

---

## 一、先搞清楚：上下文管理到底在管什么

LLM 是**无状态的纯函数**：每次请求都要把完整对话历史重新发一遍。本项目的 `history` 就是一个不断 append 的 `list[dict]`——system prompt、用户消息、助手回复、工具调用结果全在里面。它每轮只增不减，而模型的上下文窗口是有限的（本地小模型常见 4K–32K token）。不管它，长对话的结局只有一个：**请求体越来越大，直到超出窗口报错，或者被服务端静默截断后模型"失忆"**。

应对这个问题的方案光谱：

| 方案 | 做法 | 本项目用没用到 |
|------|------|---------------|
| 硬截断 | 超过长度直接砍掉头部/中部字符 | ✅ 局部用（ReAct Observation、多 Agent 累积上下文，见决策清单 **R5**） |
| 滑动窗口 | 只保留最近 N 轮，其余丢弃 | ❌ 会丢失早期关键事实（用户名字、已定的决定） |
| **摘要压缩** | 较早历史交给 LLM 浓缩成一段摘要，保留最近几条完整消息 | ✅ 主方案（本文主角） |
| RAG 历史 | 旧消息 embedding 入库，需要时检索 | ❌ 复杂度高，教学项目不划算 |

一句话概括本项目的实现本质：**把"字符数超阈值 → 让 LLM 自己把旧历史浓缩成摘要 → 同步重写数据库"这条流水线，做成两个共用函数，CLI 和 Web 各调一行**。为什么选摘要而不是别的，见决策清单 **U4**；本文只讲这套机制怎么运转。

这个机制有三个入口，共享同一套核心：

1. **自动阈值触发**：每轮回复后检查 history 总字符数，超阈值自动压缩（CLI 在 `main.py`，Web 在 `web_ui.py`）；
2. **`summarize_history` 工具**：模型自己觉得历史太长时，可以像调任何工具一样主动调用（Function Calling 工具，见 `ai_agent/app_core.py:258-268` 的 schema）；
3. **无索引截断回退**：ReAct 的 Observation、多 Agent 的 accumulated_context 等"一次性长文本"，用硬截断兜底（对应决策清单 **R5**）。

## 二、架构全景：压缩机制在整个系统里的位置

```
┌─────────────────────────────────────────────────────────────────────────┐
│                            一轮对话的完整生命周期                          │
│                                                                         │
│  用户输入 ──→ history.append(user) ──→ store.append(session, "user")    │
│                （内存）                （SQLite，main.py:274-280 /        │
│                                        web_ui.py:724-727）               │
│                     │                                                   │
│                     ▼                                                   │
│         chat_with_tools(messages=history, ...)                          │
│         → AgentRuntime 工具循环（见 runtime.py，本文不展开）              │
│                     │                                                   │
│                     ▼                                                   │
│  history.append(assistant) ──→ store.append(session, "assistant")       │
│                     │                                                   │
│                     ▼                                                   │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ 压缩触发点（每轮回复之后）                                          │   │
│  │                                                                 │   │
│  │  CLI:  main.py:307-317    total_chars > cfg.history_max_chars ? │   │
│  │  Web:  web_ui.py:691-697  同一个判断，包在 try/except 里          │   │
│  │                                                                 │   │
│  │  或：模型在工具循环里主动调 summarize_history（app_core.py:776）   │   │
│  └────────────────────────────┬────────────────────────────────────┘   │
│                               │ 命中                                    │
│                               ▼                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ ① summarize_messages()（client.py:240-295）— 纯内存压缩          │   │
│  │    短对话直接放行 → 定位 system → 边界对齐到 user 消息             │   │
│  │    → 清洗 tool 噪声 → LLM 生成摘要 → 重组新 history               │   │
│  │    （摘要失败/为空 → 硬截断回退，不崩溃）                          │   │
│  │                                                                 │   │
│  │ ② compress_and_persist_history()（app_core.py:800-813）          │   │
│  │    调 ① 拿到压缩结果 → store.clear_messages() 清空 DB            │   │
│  │    → 逐条 store.append() 重写 → 内存与磁盘一致                    │   │
│  └────────────────────────────┬────────────────────────────────────┘   │
│                               │                                         │
│                               ▼                                         │
│              下一轮请求携带的是压缩后的 history                           │
└─────────────────────────────────────────────────────────────────────────┘
```

**关键洞察：压缩不是 LLM 的内部能力，而是宿主程序的上下文工程**。模型自己不知道历史多长、也不会主动压缩；是宿主在"每轮回复之后"这个固定时机做了一次外部干预。`summarize_history` 工具只是把同一次干预的触发权下放给了模型——触发方式不同，压缩动作是同一个函数。

## 三、触发机制：字符阈值而不是 token 计数

### 3.1 阈值从哪来

`ai_agent/config.py:78-79`：

```python
# 长对话压缩阈值：history 总字符数超过该值时自动摘要压缩
history_max_chars: int = 5000
```

可用环境变量覆盖（`config.py:117`）：

```python
history_max_chars=_env_int("HISTORY_MAX_CHARS", cls.history_max_chars),
```

**为什么是字符数不是 token 数？** 精确 token 计数需要加载模型的 tokenizer（如 tiktoken / HF tokenizer），而本项目对接的是 LM Studio 的 OpenAI 兼容 API——本地模型的 tokenizer 五花八门，宿主拿不到统一接口。中文字符数 ≈ token 数是足够好的近似（1 个中文字 ≈ 1–2 token），换来零依赖、零模型绑定。这个"够不够准"的权衡见决策清单 **U4**。

### 3.2 CLI 侧：主循环里的自动触发

`main.py:306-317`，位于每轮回复持久化之后：

```python
# ===== 长对话自动摘要压缩 =====
total_chars = sum(len(m.get("content") or "") for m in self.history)
if total_chars > self.cfg.history_max_chars:
    print(
        f"\n[系统] 对话历史已达 {total_chars} 字符"
        f"（阈值 {self.cfg.history_max_chars}），自动压缩中..."
    )
    self.history = compress_and_persist_history(
        self.client, self.history, self.store, self.session_id
    )
    now_chars = sum(len(m.get("content") or "") for m in self.history)
    print(f"[系统] 压缩完成，剩余 {now_chars} 字符（保留最近 4 条完整消息）")
```

三个要点：

- **触发时机是"回复落库之后"**——即历史里已包含本轮的完整问答。这样摘要拿到的素材是完整的，且压缩动作本身不会被工具循环打断；
- `len(m.get("content") or "")` 里的 `or ""` 是必要的防御：带 `tool_calls` 的 assistant 消息 content 可以是 `None`；
- 压缩前后各打印一次字符数，CLI 用户能直观看到"10000 → 2500"这种压缩比。

### 3.3 Web 侧：同一个判断，套了层保护壳

`ai_agent/web_ui.py:691-697`：

```python
def _maybe_compress(self, state: SessionState) -> None:
    total_chars = sum(len(m.get("content") or "") for m in state["history"])
    if total_chars <= self.cfg.history_max_chars:
        return
    state["history"] = compress_and_persist_history(
        self.client, state["history"], self.store, state.get("session_id")
    )
```

调用点在 `send()` 的收尾处（`web_ui.py:800-803`）：

```python
try:
    self._maybe_compress(state)
except Exception as exc:
    self.trace(state, f"历史压缩失败: {exc}", "error")
```

与 CLI 的唯一差异：**Web 侧把压缩包在 try/except 里**。因为 `summarize_messages` 内部要调一次 LLM（见 §4.1），网络抖动或模型抽风不该让整个会话挂掉——压缩失败就打一条 trace，history 原样保留，下次超阈值再试。CLI 侧没套这层保护，压缩抛异常会被外层 `except RuntimeError` 兜住并把未回答的用户消息弹栈（`main.py:318-320`）。

## 四、核心模块拆解

### 4.1 summarize_messages()：纯内存的压缩算法

**位置**：`ai_agent/client.py:240-295`。这是整个机制的核心，输入旧 history，输出新 history，**只动内存、不碰数据库**。

#### 第一步：短对话直接放行

```python
# client.py:242-243
if len(messages) <= keep_recent + 2:
    return messages
```

消息总数 ≤ 6（4 条保留 + system + 余量）时原样返回。防止"历史本来就短还硬要摘要"的浪费——摘要是要花一次 LLM 调用的。

#### 第二步：定位 system，对齐边界到 user 消息

```python
# client.py:245-250
system_msg = messages[0] if messages and messages[0]["role"] == "system" else None
boundary = max(1 if system_msg else 0, len(messages) - keep_recent)
while boundary > (1 if system_msg else 0) and messages[boundary].get("role") != "user":
    boundary -= 1
recent = messages[boundary:]
to_summarize = messages[1:boundary] if system_msg else messages[:boundary]
```

`boundary` 先把切割点放在"倒数第 4 条"，然后**向前回退，直到落在一条 user 消息上**。为什么必须对齐到 user？因为 FC 循环会在 history 里留下 `assistant(带 tool_calls) → tool → tool → assistant` 这样的消息组；如果切割点落在组中间，保留下来的 `recent` 会以一条没有前因的 `tool` 消息开头——没有对应 `tool_call_id` 的 tool 消息是协议非法的，多数服务端会直接报错。**对齐到 user = 保证保留段永远是完整的问答/工具调用回合。**

#### 第三步：清洗噪声，拼成摘要素材

```python
# client.py:252-254
# 清洗掉 tool_calls / tool 类型的噪声消息（纯对话摘要）
clean = [m for m in to_summarize if m.get("role") in ("user", "assistant") and m.get("content")]
history_text = "\n".join(f"[{m['role'].upper()}]: {m['content']}" for m in clean)
```

待摘要区间里的 `role="tool"` 消息（工具返回的长 JSON、SQL 表格）和空 content 的 assistant 消息全部丢弃——它们是过程性噪声，摘要只需要"谁说了什么"。

#### 第四步：调 LLM 生成摘要（失败回退硬截断）

```python
# client.py:256-274
summary = None
try:
    summary = self.chat(
        [
            {
                "role": "user",
                "content": (
                    "请对以下对话历史做简洁摘要（200-300 字），保留关键事实、决定、已完成任务和"
                    "待续事项，用第三人称叙述，不要省略时间、数字、名字等硬信息。\n\n"
                    f"=== 对话历史 ===\n{history_text}\n\n=== 摘要 ==="
                ),
            }
        ],
        temperature=0.1,
        max_tokens=512,
        label="历史摘要压缩",
    )
except Exception as exc:
    log.warning("历史摘要 LLM 调用失败，回退为硬截断: %s", exc)
```

注意这次调用**不带历史、不带工具**——就是一条独立的 user 消息。摘要质量完全押在 prompt 上："200-300 字"控长度、"保留关键事实/决定/已完成任务/待续事项"控结构、"不要省略时间数字名字"防模型把硬信息泛化掉。`temperature=0.1` 压低随机性。`label="历史摘要压缩"` 不是发给模型的，是给 LLM 调用观察者的——Web UI 的 API 调用检查器里，这次摘要调用会以独立卡片出现（`label` 的流转见 `client.py:156-176` 的 `_begin_trace`），**学习者能亲眼看到"压缩"这个动作本身就是一次普通的 LLM 调用**。整段调用包在 try/except 里：LLM 服务掉线、超时等异常不再冒泡到主循环让会话崩溃，而是记一条 warning 后走第五步的硬截断回退。

#### 第五步：重组新 history

```python
# client.py:276-295
new_history = []
if system_msg:
    new_history.append(system_msg)
if summary and summary.strip():
    new_history.append({"role": "assistant", "content": f"【历史摘要】{summary}"})
else:
    # 摘要失败/为空 → 硬截断回退：丢弃较早历史，只留占位说明，保证会话不崩溃
    new_history.append(
        {
            "role": "assistant",
            "content": (
                f"【历史已截断】较早的 {len(to_summarize)} 条消息因摘要失败被直接丢弃，"
                "仅保留最近的对话内容。"
            ),
        }
    )
new_history.extend(recent)
return new_history
```

新结构 = `[system] + [一条 assistant 摘要] + [最近 4 条完整消息]`。摘要以 **assistant 角色**插入而不是 system——system 位被真正的 system prompt 占着，而 assistant 角色的"我以前说过：【历史摘要】…"在续聊时足够自然，模型会把它当作自己之前给出的背景陈述。摘要调用失败或返回空内容时，摘要位换成一条【历史已截断】占位消息——这就是硬截断回退：宁可丢掉较早历史的语义，也保证会话能继续。

### 4.2 compress_and_persist_history()：内存压缩 + SQLite 重写

**位置**：`ai_agent/app_core.py:800-813`。这是 CLI 与 Web 共用的那一层——只有 14 行，但承担了"内存与磁盘一致性"的全部责任：

```python
def compress_and_persist_history(client, history: list[dict], store, session_id: str | None) -> list[dict]:
    """摘要压缩 history，并把压缩结果重写进持久化存储（CLI / Web 共用）。返回压缩后的 history。"""
    compressed = client.summarize_messages(history, keep_recent=4)
    if session_id:
        store.clear_messages(session_id)
        # 重写当前 history（去掉 system）
        for message in compressed[1:]:
            store.append(
                session_id,
                message["role"],
                message.get("content", ""),
                message.get("tool_calls"),
            )
    return compressed
```

两个细节：

- **`compressed[1:]` 跳过 system**——数据库里从来不存 system prompt（`load_messages` 默认也会滤掉它，`persistence.py:206-207`）；恢复会话时 system 由入口处现拼（CLI 在 `main.py:348-350`，Web 在 `web_ui.py:857-859`）。这保证改 system prompt 模板不会被旧会话"锁死"；
- **`session_id` 为 None 时跳过重写**——只压缩内存（比如临时会话、评测环境），函数依然可用。

#### DB 重写的两条腿

清空：`ai_agent/persistence.py:217-225`

```python
def clear_messages(self, session_id: str) -> None:
    """清空会话的所有消息（保留会话本身）"""
    with self._lock:
        self.conn.execute("DELETE FROM messages WHERE session_id = ?", (session_id,))
        self.conn.execute(
            "UPDATE sessions SET updated_at = ? WHERE id = ?",
            (int(time.time()), session_id),
        )
        self.conn.commit()
```

重写：`persistence.py:175-188` 的 `append()`——每条消息一次 INSERT + 顺手更新 session 的 `updated_at`，`tool_calls` 字段序列化成 JSON 存列里（`persistence.py:177`），所以保留段里 assistant 消息携带的 `tool_calls` 也能完整落库。

**为什么用"清空 + 重写"而不是"删旧留新"？** messages 表没有"第几条"之外的顺序语义可用来精确表达"把 1..K 条替换成一条摘要"。DELETE 全部再逐条 INSERT，代码最短且结果与内存 `history` 严格同构——**内存是真相源，DB 只是它的镜像**。下次 `/load` 这个会话时，读出来的就是压缩后的样子，摘要效果跨进程、跨重启生效。

### 4.3 summarize_history 工具：把触发权下放给模型

自动阈值是"宿主觉得太长"，还有一种入口是"模型自己觉得太长"。

schema 注册在 `ai_agent/app_core.py:258-268`（无参数工具），system prompt 里有对应的路由指引（`app_core.py:61`：用户要求【压缩/摘要/总结对话/缩短历史】时调用）。实现是一个闭包工厂（`app_core.py:776-797`）：

```python
def make_summarize_history(client, get_history, set_history) -> callable:
    """
    生成一个 summarize_history 工具闭包。
    get_history / set_history 用于在 App 状态上读写 history（CLI / Web 各自的存储不同）。
    """

    def summarize_history() -> str:
        old = get_history()
        old_len = len(old)
        old_chars = sum(len(m.get("content") or "") for m in old)
        new = client.summarize_messages(old, keep_recent=4)
        set_history(new)
        new_len = len(new)
        new_chars = sum(len(m.get("content") or "") for m in new)
        return (
            f"✅ 对话历史摘要压缩完成！\n"
            f"  消息条数: {old_len} → {new_len}\n"
            f"  字符总数: {old_chars} → {new_chars}\n"
            f"  保留了最近 4 条完整消息，较早历史已浓缩为一段摘要"
        )

    return summarize_history
```

核心复用的还是 `client.summarize_messages(old, keep_recent=4)`——**与自动压缩同一个函数、同一个 keep_recent=4**。差异只在两点：

1. **通过 `get_history` / `set_history` 访问器间接读写 App 的 history**，因为闭包注册时拿不到未来的 history 引用；
2. **只改内存、不重写 DB**——工具返回值会作为 `role="tool"` 消息回到 FC 循环（runtime.py 的职责），DB 里照旧由主循环逐条 append，压缩结果要等下一次自动触发或会话生命周期结束时才体现到 DB 一致性上。

访问器的注册是**有条件的**（`app_core.py:517-519`）：

```python
# summarize_history 需要读写 App 自身的 history，仅在提供访问器时注册
if get_history is not None:
    tool_map["summarize_history"] = make_summarize_history(client, get_history, set_history)
```

评测等没有会话历史的入口不传访问器，这个工具就不存在——schema 与 callable 的一致性由此保证（这个"条件注册"模式见决策清单 A4）。

#### Web 侧的访问器为什么是 threading.local

CLI 的访问器简单（`main.py:163-164` 直接绑 `self.history`），Web 侧不行：所有浏览器标签页共享同一个 `AgentApp` 实例、同一份 `tool_map`，而 `summarize_history` 执行在 Gradio 的 worker 线程里，必须读写**当前这次请求**的 history。解法是 `web_ui.py:222-226`：

```python
def _get_active_history(self):
    return getattr(self._state_local, "history", [])

def _set_active_history(self, history) -> None:
    self._state_local.history = history
```

`_run_chat` 开始时把本会话 history 绑定到线程（`web_ui.py:636`），结束后读回（`web_ui.py:656`）。同一份 tool_map 在不同线程里看到不同 history，零侵入。这套机制的完整权衡见决策清单 U2。

## 五、完整流程走一遍

假设 CLI 里一个会话已经聊了 12 轮，system prompt 约 900 字符，history 共 26 条消息、合计约 5400 字符。用户又发了一句"再补充一下第三点"：


## 六、无索引截断回退：另一条降级路线

摘要压缩管的是**会话级历史**；还有一类"一次性长文本"不值得为它做摘要——比如 ReAct 某一轮的工具返回、多 Agent 不断累加的中间产出。这些走硬截断（决策清单 **R5**）：

```python
# ai_agent/demos/react.py:135-136 — ReAct Observation 截断
if len(obs) > 800:
    obs = obs[:800] + f"\n... [结果过长已截断，总长 {len(obs)} 字符]"
```

```python
# ai_agent/multi_agent.py:307-313 — 累积上下文截断
# 截断：后序子任务只需看最近 800 字 + 开头 400 字的原始任务/计划摘要
if len(accumulated_context) > 1200:
    accumulated_context = (
        accumulated_context[:400]
        + "\n…（前序产出已截断，保留最近内容）…\n"
        + accumulated_context[-800:]
    )
```

```python
# ai_agent/demos/planner.py:43-44 — Planner 模式同款
if len(prev) > 600:
    prev = "…（因篇幅较长已截断，保留最近内容）…\n" + prev[-600:]
```

两者是互补关系：**截断用于"这段文本以后不再单独重要"的场景（快、零成本、信息有损），摘要用于"这段历史以后还要持续参考"的场景（慢一次、花一次 LLM 调用、信息有损但保语义）**。multi_agent 的"开头 400 + 最近 800"两头保留策略是个折中——开头放着原始任务和计划，是后序子任务不能丢的锚点。

## 七、边界与扩展

### 这套机制不做什么（保持最小版本）

| 特性 | 状态 | 原因 |
|------|------|------|
| 精确 token 计数 | ❌ 用字符近似 | 本地模型 tokenizer 不统一，拿不到通用接口；字符数是零依赖的近似 |
| 按模型窗口动态调阈值 | ❌ 硬编码 5000 | 不知道当前模型的 context window；用 `HISTORY_MAX_CHARS` 环境变量手动调（`config.py:117`） |
| 增量/分层摘要 | ❌ 每次全量重摘要 | "摘要的摘要"质量衰减难控制；教学场景单级足够 |
| 摘要质量校验 | ❌ 摘要生成后直接采信 | 摘要丢信息是沉默的——模型忘了用户名字也不会报错 |
| tool 消息进摘要素材 | ❌ 刻意清洗掉 | 工具返回是过程性噪声（`client.py:253`），进摘要只会浪费摘要预算 |
| 摘要异步执行 | ❌ 同步阻塞 | Web 侧压缩时这轮回复已结束，用户感知就是一次额外等待 |

### 如果想扩展

1. **token 感知阈值**：启动时向 LM Studio 查模型元信息拿 context window，阈值 = window × 70%，替代硬编码 5000；
2. **结构化摘要**：把摘要 prompt 改成输出 JSON（`{"已完成任务": [...], "用户偏好": [...], "待续": [...]}`），比自由文本更抗"二次压缩衰减"——改动点在 `client.py:262-266` 的那段 prompt；
3. **失败保护（已实现）**：`summarize_messages` 的 LLM 调用抛异常或返回空摘要时，回退到硬截断（保留 system + 一条「历史已截断」占位消息 + 最近 4 条），异常不再冒泡到主循环（`client.py:256-295`）；
4. **会话恢复时的可视化**：`load_messages` 读回 `【历史摘要】` 开头的 assistant 消息时，在 CLI/Web 上给它一个特殊样式，让用户知道"这段是压缩产物，不是原话"。

### 进阶练习：把"❌"变成"动手实现"

上面表格里标 ❌ 的前两项（token 感知阈值、结构化摘要）是最值得动手的——一个改触发判断，一个改摘要格式，都只动这套流水线的一个环节。每个练习给出了源码锚点和可检查的验收标准。

#### 练习 1：token 感知动态阈值——按模型 context window 计算

> 原文方向："启动时向 LM Studio 查模型元信息拿 context window，阈值 = window × 70%，替代硬编码 5000。"

- **背景**：压缩触发判断是 `total_chars > cfg.history_max_chars`（`main.py:307-308` / `web_ui.py:691-697`），而 `history_max_chars` 硬编码 5000（`config.py:81`）。5000 字符对 32K 窗口的模型是"压缩太早浪费摘要调用"，对 4K 窗口的模型是"还没触发就爆了"——阈值和模型能力完全脱钩。
- **任务**：启动时探测当前模型的 context window（LM Studio 的模型信息接口），动态计算阈值 = window × 70% × 字符/token 换算系数；探测失败、接口不存在、字段缺失时静默回退到 `HISTORY_MAX_CHARS` 环境变量，再退到 5000。触发判断同时从"字符数"升级为"估算 token 数"。
- **提示**：项目里已有现成的 token 估算函数 `estimate_tokens`（`llm_trace.py:325-334`：CJK 字符约 1 token/字、其余约 4 字符/token，原本是给 UI 用量展示兜底用的）——把 `main.py:307` 的 `sum(len(...))` 换成 `sum(estimate_tokens(...))` 就完成了一半。另一半（探测 window）要守住这条项目级原则：**优化项不是正确性依赖**——探测失败必须静默回退，参照 MCP 连接失败降级（`mcp_client.py:580-582`）和摘要失败回退硬截断（`client.py:256-295`）的共同写法。Config 新字段（如 `context_window` / `auto_threshold`）记得写进 `validate()`（`config.py:100-127` 的收集问题模式）。
- **验收标准**：`test_core.py:466` 的 `TestConfig` 风格：mock 模型信息接口返回 window=8192，断言阈值按公式算出；接口超时/404/缺字段分别断言回退到环境变量值或 5000；显式设置了 `HISTORY_MAX_CHARS` 时断言人工值优先于自动探测；`pytest ai_agent/tests/test_core.py -k Config` 通过。

#### 练习 2：结构化 JSON 摘要——抗二次压缩衰减

> 原文方向："把摘要 prompt 改成输出 JSON（`{"已完成任务": [...], "用户偏好": [...], "待续": [...]}`），比自由文本更抗"二次压缩衰减"——改动点在 `client.py:262-266` 的那段 prompt。"

- **背景**：当前摘要是一段 200-300 字的自由文本（prompt 在 `client.py:262-266`）。长对话会触发多次压缩：第二次压缩时，第一次的摘要文本只是 `to_summarize` 里的一条普通 assistant 消息，被"再摘要一遍"——每过一次压缩，硬信息（时间、数字、名字）就被自由文本的转述衰减一轮。
- **任务**：摘要 prompt 改成要求输出 JSON：`{"已完成任务": [...], "关键事实": [...], "用户偏好": [...], "待续事项": [...]}`；**二次压缩时把旧摘要 JSON 作为结构化输入与新素材合并**（数组拼接 + 去重），而不是把它的渲染文本再丢给 LLM 转述。对 history 的呈现仍渲染成 `【历史摘要】` 开头的自然语言段落（模型和人类读的都是渲染结果，JSON 只是存储/合并格式）。
- **提示**：三个可复用的零件：① LLM 输出 JSON 的解析兜底直接抄 `_parse_critic_decision` 的三级方案（`multi_agent.py:104-150`：json.loads → 提取 `{}` 片段 → 兜底）；② "JSON → 自然语言段落"的渲染写成纯函数，方便单测；③ JSON 解析失败时回退现有的自由文本摘要路径——`client.py:256-274` 的 try/except 骨架原样保留，只是中间多一层"先试 JSON"的分支。识别旧摘要可以靠 `【历史摘要】` 前缀，更稳的做法是给摘要消息加一个 marker 字段或在渲染文本里嵌入不可见的 JSON 块。
- **验收标准**：扩展 `TestSummarizeFallback`（`test_core.py:422-451`）：mock `chat` 返回合法 JSON，断言插入 history 的摘要消息包含各字段的渲染内容；mock 返回乱码，断言回退到自由文本路径且不抛异常；模拟"压缩 → 再聊几轮 → 再次压缩"两轮，断言第二次摘要调用的输入里旧摘要是以 JSON 结构（而非渲染文本）出现的。`pytest ai_agent/tests/test_core.py -k Summarize` 通过。

## 八、总结

上下文管理与历史压缩的实现本质只有三句话：

1. **压缩是宿主的上下文工程，不是模型的能力**——每轮回复落库后检查字符阈值，超了就外部干预；`summarize_history` 工具只是把同一次干预的触发权下放给了模型；
2. **核心算法只有五步：放行短对话 → 对齐 user 边界 → 清洗 tool 噪声 → LLM 生成摘要（失败则硬截断兜底）→ 重组 `[system + 摘要 + 最近4条]`**——全部在 `client.py:240-295` 这 56 行里，边界对齐是保证 FC 协议合法性的关键一步；
3. **内存与磁盘一致靠"清空+重写"，CLI 与 Web 一致靠共用函数**——`compress_and_persist_history()`（`app_core.py:800-813`）把压缩和 DB 重写绑成一个原子动作，两端各调一行，唯一的差异是 Web 多套了一层 try/except 和 threading.local 访问器。

理解了这三点，再看这套代码会发现它短得惊人——**它没有发明任何新机制，只是把"阈值判断 + 一次普通 LLM 调用 + 一次 DB 重写"编排成了一条可复用的流水线**。
